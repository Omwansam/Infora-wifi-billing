# TR-069 / CWMP — Customer CPE management

Infora ships its own **ACS** (Auto Configuration Server). It manages *customer
premises equipment* — GPON ONTs and vendor routers at subscriber sites — over
TR-069, the standard protocol those devices speak.

---

## What this is and is not

**TR-069** is the protocol. **The ACS** is the server. The CPE calls home to the
ACS on a timer; the ACS reads its state and pushes configuration back.

> **RouterOS has no TR-069 client.** MikroTik never implemented CWMP, so this
> manages *none* of the routers in `mikrotik_devices`. Those keep using the
> existing API/SSH + WireGuard tunnel path. The two fleets never overlap:
>
> | | MikroTik routers | Customer CPE |
> |---|---|---|
> | Table | `mikrotik_devices` | `cpe_devices` |
> | Transport | RouterOS API / SSH over WireGuard | CWMP (SOAP/HTTP) |
> | Who initiates | The server | **The device** |
> | UI | Devices → Mikrotik | Devices → Customer CPE |

Devices that do work: Huawei (HG8145V5, HG8546M, EG8145V5), ZTE (F660, F670L),
and most operator-supplied GPON ONTs. Devices that don't: MikroTik, Ubiquiti,
and most retail TP-Link/Tenda firmware.

### The feature that pays for this

ONTs report **optical receive power** (`RxPower`, dBm). It is the number that
resolves most "my internet is slow" calls without dispatching anyone:

| Reading | Meaning |
|---|---|
| −8 to −25 dBm | Healthy |
| −25 to −27 dBm | Marginal — schedule a check |
| below −27 dBm | Critical — failing fibre or dirty connector |
| above −8 dBm | Too strong — ONT too close to the splitter |

It shows on the CPE list and detail page, and `GET /api/cpe/stats` counts
degraded devices.

## Running it locally

The ACS is part of the normal Flask app. In dev, compose maps **7547** (the IANA
CWMP port) to the same container, so either port works:

```bash
docker compose up -d
# ACS reachable at http://localhost:5000/tr069 and http://localhost:7547/tr069
```

Relevant env (already set in `docker-compose.yml` for dev):

| Variable | Dev default | Notes |
|---|---|---|
| `TR069_ACS_URL` | `http://<host>:7547/tr069` | What you configure on the CPE |
| `TR069_ALLOW_UNKNOWN` | `true` | Dev only — see below |
| `TR069_PERIODIC_INFORM_INTERVAL` | `300` | Also the ceiling on task delivery |
| `TR069_SESSION_RETENTION_DAYS` | `7` | Session rows pruned by `flask purge-retention` |

### Test it without hardware

`scripts/cpe-simulator.py` is a real CWMP client — it sends an Inform and
answers whatever RPCs the ACS issues.

```bash
# 1. A simulated Huawei ONT boots and registers (lands in "pending")
python scripts/cpe-simulator.py --acs http://localhost:5000/tr069 \
    --pppoe <a real radius_login> --rx-power -285

# 2. Approve it in the UI: Devices → Customer CPE → Approve
#    Then queue a WiFi change on the detail page.

# 3. The device checks in again and applies the queued work
python scripts/cpe-simulator.py --acs http://localhost:5000/tr069 \
    --pppoe <same login> --event "2 PERIODIC"
```

Pass `--rx-power -285` to simulate a subscriber whose fibre is failing
(−28.5 dBm) and watch it flag as critical.

## Two things about this protocol that shape the whole design

### 1. Changes are queued, never instant

The ACS→CPE push ("Connection Request") is an HTTP call to the device's own
address. Behind CGNAT — which is most subscribers — that address is unreachable.
**So the ACS cannot make a CPE do anything on demand.** It can only hand work
over during a session the device itself opens.

Every write endpoint therefore returns `202` with a queued task:

```json
{
  "message": "Settings change queued",
  "task": { "id": 7, "kind": "set_parameter_values", "status": "queued" },
  "queued_behind": 0,
  "delivery": {
    "mode": "next_inform",
    "expected_within_seconds": 300,
    "note": "Applies when the device next checks in (every 300s)."
  }
}
```

The UI shows `delivery.note` rather than claiming success. Lowering
`periodic_inform_interval` per device shortens the wait, at the cost of more
sessions.

### 2. Vendors share almost no parameter paths

The same setting lives in different places on different hardware:

```
InternetGatewayDevice.LANDevice.1.WLANConfiguration.1.SSID   TR-098 (Huawei, ZTE)
Device.WiFi.SSID.1.SSID                                      TR-181 (newer)
```

Optical power is a vendor extension with no standard location at all. So
nothing outside `services/tr069/profiles.py` ever names a raw path — the API
takes *semantic fields* (`wifi_ssid`, `rx_power`) and a profile resolves them.

**Adding a new ONT model is one dict in `profiles.py`.** No protocol or UI
changes. Resolution is: exact manufacturer+product class → manufacturer →
generic TR-098/TR-181 by data model root.

> Optical scaling is per-vendor (Huawei reports 0.1 dBm units). `scale_optical()`
> rejects anything outside −50..+20 dBm rather than showing a wrong number —
> a bad reading would send a technician to the wrong house.

## Auto-binding CPE to subscribers

The ONT reports its PPPoE username, which is the same credential FreeRADIUS
authenticates. The ACS resolves it through `find_customer_by_login()` and links
the CPE to that `Customer` automatically — no operator input, no MAC lists. The
subscriber name shows on the fleet list from the device's first contact.

## Security

- **Devices land in `pending`.** An ACS is reachable from the whole internet; a
  new device answers Informs but is issued no configuration until approved.
- **`TR069_ALLOW_UNKNOWN=false` in production.** Only pre-enrolled devices (with
  credentials from `POST /api/cpe/enrollment`) may register. Dev sets it `true`
  so you can point hardware at the ACS without pre-enrolment.
- **Credentials are Fernet-encrypted** via `services/encryption.py`, same as
  MikroTik passwords. The enrolment response returns the password exactly once.
- **Passwords are redacted** from task payloads returned by the API and are
  never written to logs.
- **Factory reset is admin-only and needs the serial as confirmation** — on many
  models it clears the ACS URL too, which strands the device until someone
  visits the premises.
- Rate limited by IP; expect constant background scanning on 7547 (Mirai
  legacy).

## Production deployment

Do **not** serve CWMP through the existing `billing.` vhost.

1. **DNS-only (grey cloud) `acs.<domain>` A record.** A CDN/WAF in front of CWMP
   mangles SOAP POSTs.
2. **Dedicated port 7547**, proxied to Flask like `dan-proxy-webfig.conf` does.
3. **Check TLS before committing to HTTPS.** Many budget ONTs ship TLS 1.0/1.1
   with no CA bundle and fail on modern chains. Measure what the actual fleet
   negotiates first; plain HTTP with per-device credentials on a locked-down
   vhost is a legitimate interim.
4. **Randomise inform timing.** A neighbourhood power cut brings a whole estate
   back at once. Each session holds a worker for ~1s across ~4 round trips; size
   gunicorn workers against *concurrent* sessions, not device count.
5. Set `TR069_ACS_URL` to the public URL and `TR069_ALLOW_UNKNOWN=false`.

### Getting the ACS URL onto existing ONTs

New installs are easy — configure it at the bench and pre-enrol. Already-deployed
ONTs need the URL pushed, which on GPON is normally done **via OMCI from the
OLT**. That is outside Infora unless you also manage the OLT; otherwise it is a
truck roll per device.

## Code map

| Path | Purpose |
|---|---|
| `services/tr069/soap.py` | CWMP SOAP parsing/building |
| `services/tr069/profiles.py` | Vendor parameter maps — **add new models here** |
| `services/tr069/session.py` | Session state machine, registration, task queue |
| `routes/tr069.py` | Device-facing ACS endpoint (`/tr069`) |
| `routes/cpe.py` | Operator API (`/api/cpe`) |
| `models.py` | `CpeDevice`, `CpeTask`, `CpeSession`, `CpeFirmware` |
| `components/devices/CpePage.jsx` | Fleet list |
| `components/devices/CpeDetailPage.jsx` | Detail, optical, WiFi, task history |
| `scripts/cpe-simulator.py` | Hardware-free testing |

Tables are created on boot by `ensure_schema_upgrades()` (`checkfirst=True`), in
line with the rest of the project — no Alembic migration needed.

## Not built yet

- **Connection Request (ACS→CPE push)** — the model has the fields; delivery is
  next-inform only. Where an ONT sits behind an ISP-owned MikroTik it could be
  reached over the existing management tunnel.
- **Firmware push** — `CpeFirmware` and the `Download` RPC exist; the file-serving
  endpoint and rollout UI do not.
- **Alerting on optical degradation** — the data and thresholds are there;
  it is not yet wired to `notification_dispatch`.
- **TR-369/USP** — the successor protocol. Noted, not implemented.
