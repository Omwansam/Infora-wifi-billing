# Deploying Infora / Lumen billing on a new server

Runbook for moving this stack onto a **fresh box** and re-pointing
`ruirufactorymabati.com` at it. Written for the situation you are actually in:
the old Contabo VPS (`5.189.178.15`) is down, the domain is still yours, and the
origin certificates will be regenerated from scratch.

> **Related docs**
> `config/deployment/CONTABO.md` — the *old* server's guide, where billing was
> wedged in behind the `dan` project's nginx. Keep it only as a reference for
> that shared-host arrangement (Appendix B below). **This file is the one to
> follow.**

## Part 0 — Corrections to the notes you were working from

The steps you had saved were part this project and part a different one. Fix
these before you start, or you will spend an evening on commands that cannot work:

| Your note | Reality |
|---|---|
| `npx prisma migrate deploy` | **Wrong stack.** This backend is Flask + SQLAlchemy + Alembic. Migrations are `flask db upgrade`, and the container's entrypoint already runs them on every boot. |
| `npx prisma db seed` | Seeding is `flask initdb`, also run automatically by the entrypoint. |
| Services `backend`, `redis` | Real service names: `flask_app`, `postgres`, `freeradius`, `wireguard`, `web`. **There is no redis in this stack.** |
| `ufw allow 80/tcpr` | Typo — `80/tcp`. And the firewall needs far more than 22/80 (Part 4). |
| `curl http://127.0.0.1:PORT/health` | The endpoints are `/api/test` and `/api/health/deployment`. |
| Migrations as a separate manual step | `backend/docker-entrypoint.prod.sh` runs `flask db upgrade` **and** `flask initdb` before gunicorn starts. If the DB is unreachable the container dies on boot — that is the signal, not a missing migration. |

Two more things that are true of this stack and surprise people:

- **`flask initdb` re-seeds sample LDAP/RADIUS/SNMP/VPN rows on every boot.** Those
  sample rows in a fresh console are expected, not corruption.
- **Schema changes here come from `ensure_schema_upgrades()` at boot, not from
  autogenerated Alembic revisions.** Never run `flask db migrate` on the server —
  it diffs models against a database that already has the objects and generates
  drift that crashes the next `db upgrade`.

## Part 1 — Decide the layout first (the folder question)

This is the decision that shapes everything after it, so make it now.

### What went wrong on the old server

Billing's *code* lived at `/srv/infora-billing`, but billing was never actually
self-contained. Its web tier was owned by the `dan` project under `/opt`:

```
/opt/dan/deploy/nginx/conf.d/       <- billing's vhosts lived HERE
/opt/dan/deploy/nginx/ssl/          <- billing's TLS certificate lived HERE
/opt/dan/deploy/static/infora-billing/   <- billing's built frontend lived HERE
/srv/infora-billing/                <- only the backend containers
```

`dan-proxy-1` held ports 80 and 443 and answered for billing. So:

- Billing had **no web tier of its own**. If dan-proxy stopped, billing was dark
  even though every billing container was healthy.
- The frontend was **not** built by Docker. `docker compose build` rebuilt only
  the backend; the React app had to be built by hand and copied into a directory
  belonging to another project — and if you got that path wrong, the site kept
  serving the old bundle with no error anywhere.
- Moving billing meant reconstructing three directories under `/opt` that no
  billing command knows about.

That entanglement is exactly what you are paying for now. Do not rebuild it.

### The rule for the new box

> **Everything billing owns lives under one root: `/srv/infora-billing`.**
> Code, `.env`, certificates, the built sites, the Docker volumes.
> **Nothing of billing goes under `/opt`.** If `dan` is ever installed on this
> box, the two stacks share the kernel and nothing else.

### Which path applies to you

Run this on the new server:

```bash
ss -tulpn | grep -E ':80 |:443 ' || echo "80/443 FREE"
docker ps --format 'table {{.Names}}\t{{.Ports}}'
```

| Result | Path | What billing does |
|---|---|---|
| **80/443 free** (no dan on this box) | **Path A — recommended.** Follow this document straight through. | Billing runs its **own nginx** (`infora_web`), binds 80/443, serves all four vhosts, holds its own certs. Fully separate by construction. |
| **80/443 taken** (dan or anything else is here) | **Path B** — Appendix B | Billing binds only `5080` + UDP; the existing nginx proxies to it. This is the old arrangement. Use only if you cannot free the ports. |

Path A also fixes the frontend problem permanently: `config/nginx/Dockerfile`
builds the admin console, the demo and the Lumen marketing site **inside the web
image**, so `docker compose build web` ships all three. No hand-built bundles, no
copying into someone else's directory.

**The rest of this document is Path A.**

## Part 2 — Before you wipe the old server

Do this *only if the old box is still reachable at all* — even in rescue mode. Two
of these are painful to lose:

```bash
# On the OLD server
cd /srv/infora-billing

# 1. The database — subscribers, payments, devices, RADIUS accounts
docker compose -f docker-compose.yml -f docker-compose.prod.yml \
  exec -T postgres pg_dump -U infora_user infora_billing | gzip > ~/billing-$(date +%F).sql.gz

# Volume names are prefixed with the compose project (the directory name), so
# from /srv/infora-billing they are infora-billing_*. Confirm with:
#   docker volume ls | grep wireguard

# 2. WireGuard keys — THIS ONE MATTERS.
# Losing it means every router in the field must be re-provisioned by hand,
# because the server's half of each tunnel keypair is gone.
docker run --rm -v infora-billing_wireguard_configs:/c -v ~:/out alpine \
  tar czf /out/wireguard_configs.tgz -C /c .

# 3. Uploaded ISP logos
docker run --rm -v infora-billing_isp_uploads:/c -v ~:/out alpine \
  tar czf /out/isp_uploads.tgz -C /c .

# 4. The old .env — as a reference for what was set, not to copy verbatim
cp .env ~/old.env
```

Then copy them off:

```bash
# From your local PC
scp root@OLD_IP:~/billing-*.sql.gz ~/wireguard_configs.tgz ~/isp_uploads.tgz ~/old.env ./
```

If the old box is truly unrecoverable, you are doing a clean build: the console
starts empty, and every router has to be re-provisioned (Part 12). Say so out
loud now so nobody expects yesterday's data to appear.

## Part 5 — Open the firewall

The script is the right way — it does something `ufw allow` alone cannot:

```bash
cd /srv/infora-billing
sudo ./scripts/setup-firewall.sh
```

`ufw allow` only opens the host **INPUT** chain. WireGuard runs *inside a
container*, so inbound handshakes are DNAT'd toward it and must also survive the
**FORWARD** chain, which ufw defaults to DROP. That is the failure where the
router's Tx counter climbs, Rx stays at 0, and every peer shows zero handshakes.
The script adds the `DOCKER-USER` accept rules and flips
`DEFAULT_FORWARD_POLICY="ACCEPT"`.

> `DOCKER-USER` rules survive a ufw reload and container restarts, but **not a
> full dockerd restart or a reboot**. Re-run the script after either.

Ports:

| Port | Proto | Service | Cloudflare |
|---|---|---|---|
| 22 | TCP | SSH | — |
| 80 | TCP | nginx (Cloudflare → origin) | proxied |
| 443 | TCP | nginx HTTPS (Full strict) | proxied |
| 1812 | UDP | RADIUS authentication | **must bypass CF** |
| 1813 | UDP | RADIUS accounting | **must bypass CF** |
| 51820 | UDP | Customer WireGuard VPN | **must bypass CF** |
| 51821 | UDP | Management tunnel (MikroTik) | **must bypass CF** |

**Also open the same ports in the Contabo control panel** if that VPS has a cloud
firewall. If a `tcpdump -ni any udp port 51821` on the host shows nothing at all
while a router is trying, the drop is the cloud firewall, not ufw.

Never expose 5432.

### Why the old deployment kept "losing" environment variables

`docker-compose.prod.yml` used to pass variables to the app one by one under
`environment:`. Anything set in `.env` but **not** listed there was silently
dropped — 25 variables were in that state, including all of `MAIL_*`, `SMS_*`,
`DEVICE_*` and `TENANT_BASE_DOMAIN`. It is the bug that produced the blank
captive portal (`PORTAL_BASE_URL`) and later the ignored `PLATFORM_*` settings.

The prod overlay now carries `env_file: .env` on `flask_app`, so the whole file
reaches the container. Explicit `environment:` keys still win, so nothing else
changes.

**Two rules that follow from this:**

1. An `.env` change needs `docker compose ... up -d flask_app`. Neither
   `restart` nor `build` re-reads the environment.
2. Verify passthrough with `docker inspect`, never by reading the value back out
   of the app — when the `.env` value and the code default happen to agree, a
   broken passthrough looks exactly like a working one:

```bash
docker inspect infora_flask --format '{{range .Config.Env}}{{println .}}{{end}}' | grep PORTAL
```

## Part 7 — Cloudflare DNS

You are re-pointing an existing zone, so this is edits, not a new site.

**Cloudflare → `ruirufactorymabati.com` → DNS → Records.** Change every record
below to the new IP:

| Type | Name | Content | Proxy | Why |
|---|---|---|---|---|
| A | `@` | NEW_SERVER_IP | **Proxied** (orange) | Lumen marketing site + `/api` for M-Pesa callbacks |
| A | `www` | NEW_SERVER_IP | **Proxied** | same as apex |
| A | `billing` | NEW_SERVER_IP | **Proxied** | admin console + captive portal |
| A | `demo` | NEW_SERVER_IP | **Proxied** | interactive demo |
| A | `webfig` | NEW_SERVER_IP | **Proxied** | one-click WebFig proxy |
| A | `lumen` | NEW_SERVER_IP | **Proxied** | legacy → 301 to apex |
| A | `wg` | NEW_SERVER_IP | **DNS only** (grey) | WireGuard — UDP cannot traverse the HTTP proxy |
| A | `radius` | NEW_SERVER_IP | **DNS only** (grey) | RADIUS — same reason |

**The orange/grey split is not cosmetic.** Orange = HTTP/HTTPS only. Anything
carrying UDP (RADIUS, WireGuard) must be grey or a raw IP, or it simply will not
work.

`webfig` is the exception that catches people: it **must** be orange. The origin
presents a Cloudflare Origin CA certificate, which only Cloudflare's edge trusts —
a grey record sends the browser straight at the origin and the browser rejects
the cert.

Lower the TTL to 1–2 minutes a few hours before cutover if you can, then set
**SSL/TLS → Overview → Full (strict)** once Part 8 is done. Purge the cache after
cutover: **Caching → Configuration → Purge Everything.**

## Part 8 — Certificates (Cloudflare Origin CA)

Same method you used before: generate in Cloudflare, paste into `nano` on the
server. Both files use **identical steps** — only the filename and the final
`chmod` differ.

### 8.1 Generate the new origin certificate

1. Cloudflare → `ruirufactorymabati.com` → **SSL/TLS → Origin Server**
2. **Create Certificate**
3. Let Cloudflare generate the private key and CSR (default)
4. Hostnames — make sure **both** are listed:
   - `ruirufactorymabati.com`
   - `*.ruirufactorymabati.com`
   The wildcard is what covers `billing.`, `demo.`, `webfig.` and `lumen.`
5. Validity: **15 years**
6. **Create**

You now see two boxes: **Origin Certificate** and **Private Key**.
**Leave this tab open** — the private key is shown exactly once and can never be
retrieved again.

### 8.2 Create the directory

```bash
cd /srv/infora-billing
mkdir -p certs/nginx
chmod 755 certs/nginx
```

### 8.3 Paste the certificate

```bash
nano -w certs/nginx/origin.pem
```

Copy the **Origin Certificate** box from Cloudflare and paste the whole thing,
including both marker lines:

```
-----BEGIN CERTIFICATE-----
...
-----END CERTIFICATE-----
```

Save: `Ctrl+O`, `Enter`, `Ctrl+X`.

### 8.4 Paste the private key — same steps

```bash
nano -w certs/nginx/origin.key
```

Copy the **Private Key** box from Cloudflare and paste the whole thing,
including both marker lines:

```
-----BEGIN PRIVATE KEY-----
...
-----END PRIVATE KEY-----
```

Save: `Ctrl+O`, `Enter`, `Ctrl+X`.

> `nano -w` disables line wrapping. Without it, a nano configured with
> `breaklonglines` can hard-wrap a pasted PEM line and the certificate becomes
> unparseable — with an error that points at nginx rather than at the paste.

### 8.5 Permissions

```bash
chmod 644 certs/nginx/origin.pem
chmod 600 certs/nginx/origin.key
ls -la certs/nginx/
```

Expected:

```
-rw-r--r--  origin.pem
-rw-------  origin.key
-rw-r--r--  README.md
```

### 8.6 Verify before you build

Check the certificate parses and covers the right names:

```bash
openssl x509 -in certs/nginx/origin.pem -noout -subject -dates
openssl x509 -in certs/nginx/origin.pem -noout -text | grep -A1 "Subject Alternative Name"
```

You should see `DNS:ruirufactorymabati.com` and `DNS:*.ruirufactorymabati.com`.

Confirm the key actually belongs to that certificate — the two hashes must match:

```bash
openssl x509 -in certs/nginx/origin.pem -noout -pubkey | openssl sha256
openssl pkey -in certs/nginx/origin.key -pubout | openssl sha256
```

Mismatched hashes mean you pasted a key from a different "Create Certificate"
run. Generate a fresh pair and redo 8.3–8.4; a mismatch surfaces later as a
Cloudflare **525** with nothing useful in the logs.

### 8.7 Enable the HTTPS server blocks

The HTTPS blocks ship commented out. Uncomment them in **all three** vhost
files — the old guide mentioned only `billing.conf`, which is why the other two
hostnames used to fall back to plain HTTP:

```bash
nano config/nginx/conf.d/billing.conf   # billing.ruirufactorymabati.com
nano config/nginx/conf.d/lumen.conf     # apex + www
nano config/nginx/conf.d/demo.conf      # demo.
```

In each, remove the leading `# ` from the `server { listen 443 ssl ... }` block.
The finished billing block:

```nginx
server {
    listen 443 ssl;
    http2 on;
    server_name billing.ruirufactorymabati.com;

    ssl_certificate     /etc/nginx/ssl/origin.pem;
    ssl_certificate_key /etc/nginx/ssl/origin.key;
    ssl_protocols       TLSv1.2 TLSv1.3;

    include /etc/nginx/snippets/billing-locations.conf;
}
```

The shipped comment uses the older `listen 443 ssl http2;` one-liner. That still
works on the nginx 1.25 image — it only logs a deprecation warning — so either
form is fine; the split shown above is just the current spelling.

Leave the port-80 blocks in place — Cloudflare and health checks still use them.

`docker-compose.prod.yml` already mounts `./certs/nginx` → `/etc/nginx/ssl:ro`,
so no compose edit is needed. The keys are gitignored (`certs/**/*.key`) and will
not be committed.

### 8.8 Retire the old certificate

Once the new site is verified (Part 11), go back to
**SSL/TLS → Origin Server** and revoke the old certificate. Do it **after**
cutover, not before — revocation is immediate and irreversible.

## Part 12 — The routers in the field

**They are all still pointing at the old IP.** Nothing about the server move
reaches them on its own.

```bash
# Rebuild clients.conf from the devices in the database
$DC exec flask_app flask generate-radius-clients
$DC restart freeradius
```

> Restart FreeRADIUS **every time** you add a device or rotate a secret. It reads
> `clients.conf` at startup only, and an unlisted NAS is dropped as an unknown
> client with nothing logged that names the router.

Then, per router:

- **Management tunnel routers** — the endpoint is the DNS name
  `wg.ruirufactorymabati.com`, so re-pointing that record is enough. Give them a
  few minutes; RouterOS caches DNS. A router whose clock has drifted cannot
  rejoin — NTP has to be on.
- **Direct-RADIUS routers** — the old `.rsc` baked in the **old raw IP**. Download
  a fresh RADIUS `.rsc` from the device row in the console and re-import it.
  Always download it; never copy the placeholder commands out of the UI text.
- **Hotspot routers** — after `PORTAL_BASE_URL` changes, re-run **Configure
  services** on each one so the walled garden and `login.html` are rewritten. Skip
  this and the login page is blank on every phone.

> Consider pointing `FREERADIUS_HOST` / `PUBLIC_SERVER_HOST` at a **DNS-only**
> `radius.ruirufactorymabati.com` instead of a raw IP. Routers provisioned that
> way survive the next server move as a DNS edit. It does not help the routers
> already deployed with an IP.

## Part 13 — Routine operations

```bash
cd /srv/infora-billing
export DC="docker compose -f docker-compose.yml -f docker-compose.prod.yml"
```

| Task | Command |
|---|---|
| Pull new code | `git pull --ff-only` |
| Backend change | `$DC build flask_app && $DC up -d flask_app` |
| Frontend / any `VITE_*` change | `$DC --profile bundled-nginx build web && $DC --profile bundled-nginx up -d web` |
| `.env` change | `$DC up -d flask_app` (**not** `restart`) |
| nginx or cert change | rebuild `web` as above |

**Production bakes the code into the image** — the prod overlay drops the
bind-mount with `volumes: !override`. Editing a file on the server changes
nothing until you rebuild.

### Scheduled jobs

`SUBSCRIPTION_ENFORCEMENT_INTERVAL` and `FUP_ENFORCEMENT_INTERVAL` default to `0`,
which is off — as they were on the old server. Expired subscribers are not
disconnected and FUP throttles are not applied unless you turn them on. Either set
the intervals in `.env`, or run them from host cron:

```cron
*/15 * * * * cd /srv/infora-billing && docker compose -f docker-compose.yml -f docker-compose.prod.yml exec -T flask_app flask enforce-expiry
5 2 * * *    cd /srv/infora-billing && docker compose -f docker-compose.yml -f docker-compose.prod.yml exec -T flask_app flask purge-retention
```

Other CLI commands: `poll-devices`, `enforce-fup`, `issue-subscription-invoices`,
`resume-paused`, `sync-wireguard-stats`, `diagnose-device`, `verify-deployment`.

## Part 14 — Troubleshooting

| Symptom | Cause |
|---|---|
| Cloudflare **521/522** | `web` not running, or 80/443 closed in ufw *or* the Contabo panel |
| Cloudflare **525** | Full (strict) with a bad cert: wrong paste, key/cert mismatch (8.6), or the HTTPS block still commented out |
| Site loads, login fails | `CORS_ORIGINS` missing the exact origin. `up -d flask_app` after fixing |
| Frontend changes don't appear | You rebuilt `flask_app`, not `web`. The sites live in the `web` image |
| Captive portal blank on phones | `PORTAL_BASE_URL` wrong or not reaching the container — check `docker inspect`, then re-run Configure services on each router |
| PPPoE Access-Reject | Router missing from `clients.conf`, wrong secret, or FreeRADIUS not restarted after regenerating |
| WireGuard never handshakes (Tx grows, Rx 0) | `DOCKER-USER` forward rules gone after a dockerd restart or reboot — re-run `scripts/setup-firewall.sh` |
| Routers show Offline but are up | Expected during the first minutes after cutover — `DEVICE_OFFLINE_GRACE_SECONDS` is hysteresis, not a bug |
| Container name already in use | An old `infora_*` container is still around: `docker rm -f infora_web` |
| `git pull` blocked by `clients.conf` | Part 4: `git update-index --skip-worktree config/freeradius/clients.conf` |
| A setting in `.env` is ignored | `up -d`, not `restart`; then confirm with `docker inspect`, never with the app's own output |
| `web` won't start: `host not found in upstream "flask_app:5000"` | nginx resolves the upstream **at config load**, so it refuses to boot while `flask_app` is missing. Start `flask_app` first, then `web`. For the same reason, **restart `web` after recreating `flask_app`** — nginx caches the old container IP until reloaded |

Poking at live data inside the container needs the working directory set, because
the image copies the repo to `/app`:

```bash
docker exec -w /app/server infora_flask python -c "from models import Customer; print(Customer.query.count())"
```

## Appendix A — TR-069 / CWMP ACS over a public vhost

> **The ACS is already running in production over the management tunnel — this
> appendix is not how it is deployed, and you almost certainly do not need it.**
>
> The live configuration is `TR069_ACS_URL=http://10.250.0.1:7547/tr069`. **Do not
> blank it.** An earlier version of this appendix said TR-069 had "no route in
> production" and told you to leave the variable empty; that was true only of the
> public-vhost path below, and following it now switches off a working ACS.
>
> Nothing is published to the internet: the wireguard container DNATs
> `10.250.0.1:7547` → `flask_app:5000` (`ensure_acs_forward` in
> `config/wireguard/custom-cont-init.d/99-apply-flask-wg.sh`), and every managed
> router already routes `10.250.0.1/32` down the tunnel. Port 7547 being unpublished
> and nginx proxying only `/api/` is the *point*, not a gap. Verify the path with
> `flask diagnose-acs`.

**This appendix applies to one case only: CPE that are NOT behind a managed
MikroTik**, and so cannot reach `10.250.0.1`. For everything else use the tunnel —
no internet exposure, no CDN/WAF mangling SOAP, no TLS-chain failures on budget
ONT firmware. See `TR069.md`.

To expose a public ACS anyway, in `docker-compose.prod.yml` under `flask_app`:

```yaml
    ports: !override
      - "5080:5000"
      - "7547:5000"
```

Then a **DNS-only** (grey cloud) `acs` record, `ufw allow 7547/tcp`, and:

```bash
TR069_ACS_URL=http://acs.ruirufactorymabati.com:7547/tr069
TR069_ALLOW_UNKNOWN=false
```

Grey cloud is mandatory: a CDN/WAF in front of CWMP mangles the SOAP POSTs, and
budget ONTs fail on modern TLS chains. Keep `TR069_ALLOW_UNKNOWN=false` — the ACS
faces the whole internet. See `TR069.md`.

Switching to a public ACS URL also disables the enrolment window
(`POST /api/cpe/enrollment-window`), which refuses to open unless the ACS is
tunnel-only. On a public vhost, pre-enrol every CPE by serial instead.

## Appendix B — If the new box also runs `dan` on 80/443

Only if you cannot free the ports. This reproduces the old arrangement, with its
drawbacks (Part 1).

Billing runs **without** the bundled nginx — omit `--profile bundled-nginx`, so
no `infora_web`, and Flask is reached on `5080`:

```bash
$DC up -d          # postgres, flask_app, freeradius, wireguard
curl -s http://127.0.0.1:5080/api/test
```

The frontend is then **not** built by Docker and must be built and published by
hand — this is the step that silently serves a stale bundle when the destination
path is wrong:

```bash
cd /srv/infora-billing/FRONTEND/infora_billing
npm ci
VITE_API_BASE_URL=https://billing.ruirufactorymabati.com \
VITE_RADIUS_SERVER=NEW_SERVER_IP \
VITE_MARKETING_URL=https://ruirufactorymabati.com \
npm run build

# Publish into the proxy's static root, preserving sibling sites.
DEST=/opt/dan/deploy/static/infora-billing
rm -rf "$DEST/assets"
find "$DEST" -maxdepth 1 -type f -delete
cp -a dist/. "$DEST/"        # never rm -rf the whole dir — _demo/ and _lumen/ live there
```

Verify the live bundle actually changed:

```bash
curl -s https://billing.ruirufactorymabati.com/ | grep -oE 'index-[a-z0-9]+\.js'
```

Vhosts to copy into the proxy's `conf.d`, adjusting paths:

- `config/deployment/dan-proxy-ruirufactory.conf` — apex, www, billing
- `config/deployment/dan-proxy-webfig.conf` — the WebFig proxy
- `config/deployment/nginx-external-proxy.conf.example` — generic template

They proxy to `http://172.17.0.1:5080` because a containerised nginx cannot reach
the host's `127.0.0.1`. `proxy_set_header Host $host` is required — the WebFig
proxy routes on the Host header.

Reload without recreating the container (it fronts other live sites):

```bash
docker exec dan-proxy-1 nginx -t && docker exec dan-proxy-1 nginx -s reload
```

The certificates then belong to that proxy, not to billing — install the same
`origin.pem` / `origin.key` from Part 8 wherever it mounts its SSL directory.
